## Fix 502s: move password-reset commit to a background job (repair-job pattern)

**Root cause:** synchronous commit does ≤50 sequential Graph resetPassword calls (with 202 polling) inside one HTTP request; Railway's proxy kills it → 502. The repo's established fix for this is the django-q2 repair-job pattern (`MicrosoftRepairJob` + `@django_q_task @tenant_async` + per-record progress + FE polling).

### Backend — `app_microsoft`
1. **Model**: add `TargetType.PASSWORD_RESET` to `MicrosoftRepairJob` (TextChoices only — no migration needed; `max_length=32` already). Job table is shared with repair jobs; the generic detail view serves both.
2. **`password_reset_bulk.py`**:
   - `start_password_reset_job(tenant, raw_emails, raw_password)`: validate password (existing `_parse_password`), parse/preview emails, create job with `candidate_ids = [eligible user ids]`, pre-seed `results` with skipped rows (`not_found` / `no_microsoft_account`), dispatch runner via `.delay(job.id, schema, password)`.
   - `run_password_reset_job(job, tenant, password)` decorated `@django_q_task @tenant_async(entity=MicrosoftRepairJob)`: per eligible user → `reset_password` → persist counters/results after each record (copy `_persist_progress`/`_finalize` helpers' approach from `repair.py`), pace with existing `_MS_GRAPH_MUTATION_GAP_SEC` (0.45s) between records, terminal status succeeded/partial/failed per repair semantics.
   - Password travels via django-q2 task args (Redis db 4) — acceptable for an internal bulk tool; noted, not persisted in the DB row.
3. **Timeout**: extend the `@django_q_task` shim (`utilitas/async_tasks.py`) to pass through django-q2's `timeout` option; dispatch with `timeout=3600` (qcluster default is 900s; 900+ emails × ~1s worst case can exceed it).
4. **Views/URLs**: `POST microsoft/password-reset/jobs` `{emails, organization_id, password?}` (RBAC `microsoft.repair`, same base view as other password-reset endpoints) and `GET microsoft/password-reset/jobs/<id>?organization_id=`. Existing `MicrosoftRepairJobDetailView` pattern reused; `serialize_repair_job` works as-is.
5. **Guardrail**: sync `commit` endpoint stays (dev/small fallback) but `MAX_EMAILS` drops 50 → 20 to keep it under the proxy ceiling; FE stops using it.
6. **Trim 202 polling**: `OPERATION_POLL_ATTEMPTS` 5 → 3 for the sync path (job path is unaffected by HTTP timeouts).

### Frontend — `schedjuice-reimagined-fe`
7. **`client-api/microsoft.ts`**: `startMicrosoftPasswordResetJob(emails, organizationId, password?)` + `getMicrosoftPasswordResetJob(id, organizationId)` + job payload types (repair-job shape; results rows `{email, status, reason}`).
8. **`page.tsx`**: replace the commit batch loop with: start job → poll query (2s `refetchInterval` until terminal status, copying `microsoft-bulk-repair/page.tsx` incl. `useQueryState("job")` so reloads re-attach) → render live counters + results from `job.results`, keep CSV export and the password input. Preview flow unchanged (local DB, fast). `runBatchesSequentially` remains for preview only.

### Tests — `app_microsoft/tests/`
- `test_password_reset_bulk.py`: job start (candidate resolution, skipped pre-seed, invalid password → `BulkPasswordResetError` before dispatch, `.delay` called), runner success/partial/failure paths (mock `MSUser`, mock `.delay`).
- `PasswordResetBulkApiTests`: POST jobs endpoint (RBAC 403 for teacher, 200 + job payload for superadmin, unknown org 400), GET detail progress.
- Existing sync-commit tests updated for `MAX_EMAILS = 20`.
