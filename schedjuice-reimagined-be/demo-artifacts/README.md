# Demo Artifacts

Maintained YAML and optional import files for provisioning demo tenants via the Demo Blueprints
workflow. Generated demo scripts are written to `demo-scripts/` and are not version-controlled.

## Directory layout

```
demo-artifacts/
  README.md
  blueprints/          # Niche templates (org toggles, terminology, academic structure)
  scenario-packs/      # Reusable seed bundles (CRM leads, unpaid students, today's classes, …)
  use-cases/           # Pain point → routes, talking points, required scenario packs
  briefs/              # Per-lead overlays (school name, pain points, demo date, import refs)
  imports/             # Optional sanitized spreadsheets referenced by briefs
  demo-scripts/        # Generated output (gitignored; regenerated by provision-demo)
```

| Directory | Purpose | Version-controlled |
|-----------|---------|-------------------|
| `blueprints/` | One YAML per niche (e.g. tutoring center, K12, Montessori) | Yes |
| `scenario-packs/` | Shared, composable seed bundles | Yes |
| `use-cases/` | Maps pain points to demo stops and scenario packs | Yes |
| `briefs/` | Per-lead config checked in for team sharing | Yes |
| `imports/` | Optional sanitized spreadsheets for merge import | Yes |
| `demo-scripts/` | Markdown + JSON tour generated after provisioning | No (gitignored) |

## Provision a demo tenant

From the backend repo root:

```bash
python manage.py provision-demo \
  --blueprint tutoring-center \
  --brief demo-artifacts/briefs/sunrise-tutoring.yaml
```

Optional flags: `--reset` (wipe and rebuild an existing demo tenant with the same slug),
`--dry-run`, `--skip-import`.

The command prints tenant URL, demo account credentials, script path, and the value to use for
local dev (see below).

### Yangon Montessori (YMEC) — tuition + staff campus check-in

```bash
python manage.py provision-demo \
  --blueprint montessori \
  --brief demo-artifacts/briefs/yangon-montessori.yaml \
  --reset \
  --skip-import
```

Seeds MMK child tuition (client-realistic course fees and payment channels) and June staff
`BuildingCheckin` rows for `/services/campus-checkins`. Demo accounts: `demo-finance@…` for
student payments, `demo-teacher@…` (Class Advisory) for campus check-in.

## Optional lead import (with mapping sidecar)

Briefs can include an `import:` block to merge sanitized spreadsheet rows into the tenant after
scenario packs are seeded:

```yaml
import:
  file: demo-artifacts/imports/sunrise-roster.csv
  mode: merge
```

- `file` is resolved from the backend repo root.
- Supported formats: `.csv`, `.xlsx`.
- `mode`:
  - `merge`: keep existing seeded data and add imported users.
  - `replace_fiction`: remove fiction-pattern users/courses before import, while preserving
    `DEMO-` course anchors.

For non-obvious headers, add a sidecar mapping file next to the spreadsheet:

`demo-artifacts/imports/sunrise-roster.mapping.yaml`

```yaml
role: student
columns:
  Student Name: name
  Email: email
  Phone: phone_number
  Date of Birth: date_of_birth
  Class: course_title
```

If headers are ambiguous and no sidecar exists, provisioning writes a template mapping file to
`demo-artifacts/imports/{slug}.mapping.template.yaml` and exits with a validation error.

## Local development

After provisioning:

1. Set `DEV_TENANT_DOMAIN` in the backend `.env` to the `domain_url` printed by the command.
2. Restart the backend server.
3. Open an incognito browser window, clear any stale `tenant` / `schema` / `access` cookies, and
   log in with the printed demo credentials (e.g. `demo-admin@{domain_url}`).

For API-only checks, send the `X-Tenant: xdemo_{slug}` header instead of changing cookies.

## Team rule: fictional data only

**Briefs and imports must use fictional or sanitized data only.** Do not commit real student PII,
parent contact details, or lead spreadsheets from production. Use made-up names and scrubbed
spreadsheets so briefs can be shared and iterated on safely in git.
